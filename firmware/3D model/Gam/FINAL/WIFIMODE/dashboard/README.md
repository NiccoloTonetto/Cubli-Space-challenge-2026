# Balance console — local web dashboard

Live charts, a 3D attitude view with the resolved pivot highlighted, and
buttons for the real command grammar. Same UDP transport, same heartbeat and
same CSV format as `telemetry_python_wifi_corner.py` / `telemetry_python_wifi.py`,
which are **left untouched** — this is a parallel front end, not a replacement
for those files.

```
pip install -r requirements.txt
python app.py                 # -> http://127.0.0.1:8000
```

## Before you run it

**Close the matplotlib scripts first.** This binds UDP `:4210`, so it cannot
share the port with `telemetry_python_wifi*.py` or `terminal_wifi.py`.

The firmware must be in `PLOTMODE` (the default in both WiFi sketches), the
Teensy in `t1` (WiFi) and the XIAO in `x1` (TEENSY_BRIDGE) — the same
preconditions the existing scripts need. `--target` defaults to `172.20.10.14`,
matching `XIAO_IP` in `xiao_teensy_bridge.ino`.

## Desk test, no hardware

```
python app.py --target 127.0.0.1 --target-port 4211    # terminal 1
python replay.py                                       # terminal 2
```

`--target-port 4211` is required on loopback. The server listens on 4210, so
telling it to send commands to 127.0.0.1:**4210** would point it at its own
bound port: it would talk to itself, `replay.py` would never hear a command,
and every button would look dead. `replay.py` therefore listens on 4211. On
real hardware the XIAO is a different host, the collision cannot arise, and
both sides use 4210 — so the bench command has no `--target-port`.

Two things that look wrong in desk mode but are not: the **ARMED pill stays
DISARMED** no matter what you press, because it is driven by the `armed`
telemetry column (authoritative — it catches a self-disarm on a trip) and that
recording has `armed = 0` throughout; and **ARM stays greyed out**, because
the run starts at |φ| ≈ 55°, far outside the gate.

`replay.py` re-emits the newest `telemetry_corner_*.csv` from `../../telemetry/plot/`
at its recorded timing and injects the firmware's `#` console lines, so the
parsers, the pivot highlight and the arm-gate learning all get exercised.
`--schema edge` synthesizes a 10-field stream to test auto-detect and the
schema switch. `--speed 4` scrubs faster; `--once` stops instead of looping.

## What the controls actually do

| Button | Sends | Notes |
|---|---|---|
| ARM | `a1` | two-step confirm; disabled while `\|φ\| ≥` gate, and the server refuses it too |
| DISARM | `a0` | header, always visible. **Spacebar** does the same from anywhere |
| HALT / RESUME | `p1` / `p0` | corner build only — the edge build has no halt |
| RE-RESOLVE | `c` / `e` | the only way to learn which corner/edge is active |
| TARE φ / CLEAR φ | `z1` / `z0` | corner only; the edge build uses `o<deg>` instead |
| Gain | `g<0..1>` | debounced slider |

Every accepted command is echoed into the console pane as `> a0` in cyan the
moment it goes on the wire, with the firmware's own `#` reply following in
grey. That matters because some commands never reply — the edge build gates
most echoes behind `SERIALMONITORMODE` — so without the outbound echo a
working press and a dropped UDP packet look identical.

There is **no** `RUN_EDGE_CODE` / `RUN_CORNER_CODE`. Edge vs corner is decided
by which sketch is flashed. The AUTO/EDGE/CORNER buttons only tell the
dashboard how to read the stream — 10 fields is the edge build, 21 the corner
build — they do not change the cube.

Every command from the browser is validated against the per-schema grammar in
`schemas.py` before it reaches the socket. `h1`/`h0` are deliberately not
accepted: on the WiFi builds `h` is the link keepalive and halt moved to `p`,
so `h1` would be silently swallowed. The keepalive is generated by the
heartbeat thread, never by a client.

## Two things worth knowing

**The arm gate is not 0.5 deg.** Three values are live in the tree:

| where | rad | deg |
|---|---|---|
| `Gam/cubli_gains.h:40` `ARM_GATE` | `0.00872664619` | 0.50 |
| `CornerBalance_WiFi.ino:584` `kArmGate` | `0.01745329252` | 1.00 |
| `EdgeBalance_WiFi.ino:484` `kArmGate` | `0.1672664619` | **9.58** |

The edge number looks like a typo of the header's (shared `72664619` tail) and
its comment still claims 0.5 deg — as flashed, that build will accept `a1`
with the cube leaning ~9.6°. **Not fixed here**: it is validated control
firmware and wants its own change plus a bench re-test.

So nothing in this tool hardcodes a gate. It assumes the conservative 0.50°
until the firmware states its own value in an `# ARM REFUSED: … ARM_GATE=X.XX`
line, then shows what it actually said and raises a banner if that exceeds
1.5°. Note `telemetry_python_wifi_corner.py:102` and `plot_session_csv.py:158`
both hardcode 0.5, so the dashed gate line on the existing corner plots is
drawn at half the real threshold.

**There is no battery telemetry.** Neither wire format carries voltage or
current, so the tile the spec asked for would have been fabricated. It shows
link health instead — packet rate, age, count, gain — which is what actually
answers "is it safe to arm".

## Files

| | |
|---|---|
| `app.py` | server: UDP socket, three I/O threads, WebSocket fan-out, CSV lifecycle |
| `schemas.py` | wire formats, pivot geometry, `#`-line regexes, command whitelist |
| `replay.py` | offline simulator |
| `static/` | `index.html`, `app.js`, `cube_vis.js`, and the vendored libraries |

Recordings go to `../../telemetry/plot/` with the same names and the same
header row as the matplotlib scripts write, so `plot_session_csv.py` reads
them unchanged (verified). Unlike those scripts, writing is incremental —
a run that ends in a crash still leaves a usable file.

The frontend libraries are vendored into `static/vendor/` (~1.3 MB) rather
than pulled from a CDN: the bench runs off a phone hotspot and the instrument
must not blank when cellular drops.

## Why threads and not asyncio for the I/O

`CornerBalance_WiFi.ino:170` sets `kLinkTimeoutMs = 300`, so an armed cube
auto-disarms if the link goes quiet for that long. The 100 ms `h` heartbeat is
therefore the most safety-critical thing this process does, and it must not
queue behind JSON serialization, a slow browser socket or a GC pause. All I/O
stays on plain threads — the pattern the existing scripts already prove — and
asyncio only fans telemetry out to browsers, where being late costs nothing
but a stuttery chart. The handoff is a bounded `deque`, whose `append` and
`popleft` are atomic under the GIL.

Consequences worth stating: closing the browser changes nothing on the cube,
because the heartbeat is independent of clients. Killing the server disarms it
within 300 ms, which is the existing failsafe doing its job. Display data is
decimated to 20 Hz batches; the CSV always gets every sample.
